# session-usage

Claude Code のセッション記録（`~/.claude/projects/*/*.jsonl`）からトークン使用量とコストを集計するスクリプト。

`/cost` より細かく、「何にトークンを使ったか」「コンテキストがどう肥大したか」まで見えます。

このツールは目的を2つに分けています。

- **実測集計** — 記録された使用量とモデル別単価から、できるだけ正確にコストを出す
- **仮想試算**（`--simulate`） — 明示した仮定のもとで、委譲したときの相対差を見る

`--simulate` の出力は実測値の延長ではなく、仮定ベースのシナリオです。混同しないよう出力列を分けています。

## 使い方

```bash
python3 analyze.py                # 全セッションの要約
python3 analyze.py -p xrev        # プロジェクト名で絞り込み
python3 analyze.py -d             # コンテキスト推移と会話内容の構成比
python3 analyze.py --tasks        # タスク別の時間とトークン
python3 analyze.py --simulate     # 分担した場合のコスト試算
```

依存パッケージはありません（標準ライブラリのみ）。

## テスト

```bash
python3 -m unittest discover -s tools/session-usage/tests
```

## 出力の見方

### 要約

```
プロジェクト                     session   ターン  sub        入力      出力   入:出        $
-Users-naokami-Works-xrev      ff13b58b     362    0 128,768,747  467,061   275:1    79.48
```

- **sub** — サイドチェーン（サブエージェント）内の**課金ターン数**。サブエージェントの
  「呼び出し回数」ではありません。JSONL からサブエージェントを一意に識別できる
  フィールドが確認できていないため、呼び出し回数は集計していません
- **入:出** — 入力トークンと出力トークンの比。コーディングセッションでは 50:1〜400:1 になり、**コストの大半は出力ではなく入力**（毎ターン再送されるコンテキスト）が占める

### 詳細（`-d`）

コンテキストの四分位推移で、セッション中にどれだけ肥大したかが分かります。

```
第1四分位: 平均    78,549 tok
第4四分位: 平均   231,479 tok
```

後半ほど1ターンあたりの単価が上がるため、**セッションを適切に区切ることは、モデル選択と同等かそれ以上の削減手段**になります。

会話内容の構成比では、思考・ツール呼び出し・ツール実行結果の割合が出ます。実測では思考が46〜54%を占めており、effort 設定の見直しも独立した削減手段です。

### タスク別（`--tasks`）

```
系列     カテゴリ            ターン       生成      ツール待ち      出力tok       入力増分         処理入力        $
メイン    実装              132    1h02m         7s    276,992    262,741   27,299,000    22.09
メイン    調査(コード)          48    6m47s         4s     24,603     94,389    6,487,870     6.23
```

**時間の測り方**

セッションの物理レコードを時刻順に並べ、隣接する区間を重複なく次のラベルに分けます。
カテゴリ別の時間を足すとセッション総時間に一致します。

- **生成** — モデルが応答を書いていた区間。`ts(assistant)` は当該メッセージの完了時刻です
- **ツール待ち** — 未完了の `tool_use` がある区間。並列実行でも最後の結果が届くまでを1区間として扱い、重複計上しません
- **未説明** — 上のどれにも当てはまらない区間。値を捨てずに表示します

ユーザーの応答待ち（`AskUserQuestion` の回答待ち、次のプロンプトまでの待機）は**計測しません**。
待っている間は API を呼ばないため、トークンを消費しないからです。ただしツール待ちに混ぜると
実行時間が数十時間に膨らむので、内部では区別して除外しています。

計測終端はターン最後の実レコードです。`tool_result` が欠落したターンでも、離席時間がツール待ちへ流れ込みません。

**ツール別の応答待ち**

`--tasks` は、ツールごとに「発行してから結果が返るまで」の秒数も出します。カテゴリ別の時間が
「どの作業に時間がかかったか」を示すのに対し、こちらは「どのツールが待たせているか」を示します。

```
ツール                        回数        合計      中央値      p90       最大
Bash(cat)                  52    17m00s       6s      56s    1m01s
Bash(ls)                   28    14m21s       0s      15s   13m03s
```

Bash はコマンドの先頭を添えて `Bash(cat)` の形にします。オプションや記号で始まるセグメント
（複数行コマンドの継続行）はコマンド名として採用しません。

**並列実行したツールは同じ時間帯を共有するため、合計は実時間を超えることがあります。**
カテゴリ別の時間（重複なしの区間分割）とは別の見方なので、足し合わせて比較しないでください。
中央値と最大値を並べているのは、合計が「全体的に遅い」のか「数件の外れ値」なのかを
切り分けるためです。

**重複読み取り**

同一セッションで2回以上読んだファイルを警告に出します。編集のたびに読み直していないか、
同じ調査を繰り返していないかを見るためです。

```
警告: 同一セッションで2回以上読んだファイルが 8件
  余分な読み取り 11回 / コンテキストに入る読み取り全体 112回（10%）
      3回  plugins/pattern-radar/skills/pattern-radar/scripts/detect.rb
```

`cat x | grep y` のようにパイプやリダイレクトで別コマンドへ渡した読み取りは、内容が
コンテキストに入らないため数えません。ここを区別しないと実態の倍近く多く見えます
（実測では 112回に対しパイプ経由が 84回ありました）。

別セッションでの再読み込みは文脈が違うので重複としません。

**検算**

`system` レコードの `turn_duration`（`durationMs`）とターン単位で突き合わせ、最大絶対誤差と最大相対誤差を出します。
ユーザー確認待ちを含むターンは意味が揃わないため除外し、件数を表示します。

**トークンの3列**

- **出力tok** — そのターンの出力。タスク固有量として扱えます
- **入力増分** — 前ターンからのコンテキスト増分の**推定値**。圧縮・モデル切替・初回のターンは加算しません
- **処理入力** — `input + cache_read + cache_creation` の総量。過去のコンテキストを含む課金上の処理量であり、タスク固有量ではありません

**分類**

ツール名で決まるもの（Read/Grep/Glob → 調査(コード)、Edit/Write → 実装、AskUserQuestion → ユーザー確認）と、Bash のコマンドを見て決めるもの（テスト実行 / lint実行 / バージョン管理 / スクリプト実行）があります。ツールを呼ばないターンは相談です。

`cat` `ls` `grep` `find` `wc` などファイルの中身や場所を見るコマンドは、Read/Grep ツールと同じ用途とみなして**調査(コード)** に寄せています。厳密な区別より、未分類を減らして時間とトークンの行き先を見せることを優先しました。

スクリプト実行は**言語名まで出します**（`スクリプト実行(Python)` `スクリプト実行(Ruby)` など）。
ただし `python3 -m pytest` のようにテストや lint を起動している場合は、そちらを優先します。

Bash は**実行コマンドの位置だけ**を見ます。引用文字列とヒアドキュメント本文を落としてから `;` `&&` `||` `|` で分割し、先頭の環境変数代入・`cd`・ラッパー（sudo/time/env/xargs など）を剥がした残りで判定します。全文への正規表現だと `echo "pytest を実行"` やファイル名 `test_analyze.py` にも一致してしまいます。

コマンド置換・サブシェル・制御構文・`bash -c` の入れ子など、限定文法で扱えない構文は**解析不能**として数えます。「その他」に混ぜると分類できていない事実が見えなくなるためです。分類率と未分類コマンドの先頭は警告に出ます。

1ターンが複数カテゴリに該当した場合は優先順位で1つに寄せ、混在した件数を警告に出します。

### 試算（`--simulate`）

実装系ツール（Edit/Write/Bash 等）を使ったターンを、より安いモデルのサブエージェントに委譲した場合を試算します。委譲したターンが生んだコンテキスト増分は、以降メイン側に積まれないものとして計算します。

`claude-dev-orchestration-ja` プラグインを導入する価値があるかの目安に使えます。

出力は3種類の金額を並べます。

```
実測$  比較基準$  委譲案$  基準比
36.83     30.77    25.62  -16.7%
```

- **実測$** — 記録された使用量とモデル別単価から算出した実測コスト
- **比較基準$** — `--main-model` で全ターンを処理し、入力を全てキャッシュ読み込み単価で近似した場合
- **委譲案$** — **同じ価格前提**で計算した分担案
- **基準比** — 比較基準$ と 委譲案$ の比較

実測$ と 比較基準$ は前提が違うので一致しません。異なる価格前提どうしを比較しないよう、削減率は比較基準$ を基準に取っています。

既存のサイドチェーンは主系列とコンテキストの増分を共有できないため、試算の対象から除外し、除外ターン数を末尾に表示します。

#### 試算の仮定

すべてCLIで上書きできます（既定値は括弧内）。

| オプション | 既定 | 意味 |
|---|---|---|
| `--main-model` | `claude-opus-5` | メイン側のモデル |
| `--delegate-model` | `claude-sonnet-5` | 委譲先のモデル |
| `--handoff-input` | 40000 | 引き継ぎ1回の入力トークン |
| `--handoff-output` | 2500 | 引き継ぎ1回の出力トークン |
| `--review-turns` | 10 | レビュー1パスのターン数 |
| `--review-input-start` | 20000 | レビュー初回の入力トークン |
| `--review-input-step` | 9000 | レビュー1ターンあたりの入力増分 |
| `--review-output` | 1200 | レビュー1ターンの出力トークン |
| `--sub-initial-context` | 3000 | サブエージェントの初期コンテキスト |

レビューの「1パス」は内部的に `--review-turns`（既定10）ターンを想定しています。

#### 精度について

- サブエージェントの重複読み込み（メインが読んだファイルを読み直す分）を計上していない → 分担側を**過小**評価
- 委譲対象を実装ツール使用ターンのみに限定 → 実際の実装フェーズはより広いため**過大**評価
- 引き継ぎとレビューのコストは仮置き

**本試算は仮定への感度が高く、精度を保証しません。複数のパラメータ設定で削減傾向が維持されるかを確認する用途に限定してください。**

```bash
# パラメータを振って傾向が変わらないか見る
python3 analyze.py --simulate --review-turns 5
python3 analyze.py --simulate --delegate-model claude-haiku-4-5
```

## 単価について

`PRICE` 定数に**モデルID単位**で単価をハードコードしています（前方一致で判定）。

同じ価格帯でも世代によって単価が変わるため、`"opus" in model_name` のような価格帯名の部分一致では判定していません。部分一致にすると、新しいモデルを黙って古い単価で計算してしまいます。

未登録のモデルは**コストに計上せず**、実行後に警告を出します。

```
警告: 価格未登録のモデルがあり、コストに含まれていません
  claude-opus-4-1  42ターン
  未計上トークン合計: 1,234,567
  analyze.py の PRICE に単価を追加してください。
```

この場合は `PRICE` に単価を追加してください。終了コードは変わりません（厳密な用途向けに、将来 `--strict-pricing` を追加できます）。

**キャッシュ書き込み単価の 1.25 倍は 5分TTL 前提**です。1時間TTL は 2 倍ですが、JSONL から TTL は判別できないため一律 1.25 倍で計算しています。1時間TTL を多用している場合はキャッシュ書き込み分を過小評価します。

公表価格の変更に追従していない可能性があるため、金額を根拠に判断する場合は最新の価格表と突き合わせてください。サブスクリプション利用時は、金額ではなく利用上限の消費ペースとして読み替えます。

## 品質の検証について

コスト削減と引き換えに出力品質が落ちていないかは、このスクリプトでは測れません。別途、以下の客観指標で比較します。

1. テスト初回通過率 — 修正ループに入らず完了したか
2. 修正ループの周回数
3. ユーザーの差し戻し回数
4. 差分の大きさ（`git diff --stat`）— 必要以上に触っていないか
5. 受け入れ基準の充足数

**手順:** 同一の開始コミットから同じタスクを2アーム実行し（`git worktree` で分離）、アームの実行順を交互に入れ替えて順序効果を消します。主観評価が必要な部分は、どちらのアームか伏せて差分だけを独立したレビューエージェントに渡します。

最小構成として、実タスク1件を worktree で2回やるだけでも、テスト初回通過と差し戻し回数の差は見えます。
