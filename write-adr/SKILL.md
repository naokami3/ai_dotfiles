# ADR 作成ガイド

技術的な意思決定を `docs/adr/NNNN-<slug>.md` に記録する。

## いつ ADR を書くか

- 翻訳エンジンやライブラリの選定・不採用を決めたとき
- アーキテクチャパターンを変更したとき（デコレータ導入、HTTP クライアント変更等）
- linter 警告への対処方針を決めたとき
- 「なぜこうしたのか」を将来の開発者が疑問に思いそうなとき

## フォーマット

```markdown
# ADR-NNNN: タイトル

- **Status:** Accepted | Superseded | Deprecated
- **Date:** YYYY-MM-DD
- **Decision makers:** @username

## Context

なぜこの判断が必要になったか。問題や背景を記述。

## Candidates（検討した選択肢がある場合）

### A. 選択肢A
- 特徴、メリット、デメリット

### B. 選択肢B
- 特徴、メリット、デメリット

## Evaluation（実測データがある場合）

実際に試した結果。コード例、ベンチマーク、品質比較など。
データに基づく判断であることを示す。

## Decision

**何を選んだか。** 理由を簡潔に。

## Consequences

この判断の結果、何が変わるか。
- 良い影響
- トレードオフ
- 将来の課題
```

## 書き方の原則

- **判断の根拠を残す**: 「X を不採用にした」だけでなく「X を試したが Y の理由で不採用」
- **実測データを含む**: 可能な限りベンチマーク、品質比較、メモリ使用量の実測値を記録
- **不採用理由も記録**: 将来同じ選択肢が提案されたときに再調査を避ける
- **短く**: 1-2ページに収める。詳細はコードやコミットメッセージに委ねる

## 番号の採番

`docs/adr/` 内の既存ファイルの最大番号 + 1。ゼロパディング4桁（0001, 0002, ...）。

## 参考: よくある ADR のテーマ

- ライブラリ/フレームワークの選定
- データベース/ストレージの選択
- API 設計の方針
- 認証/認可の方式
- テスト戦略の変更
- パフォーマンス最適化の判断
- ライセンス互換性の判断
- linter/formatter の警告への対処方針
