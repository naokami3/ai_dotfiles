# 設計→実装→レビュー オーケストレーション

このskillを起動したセッションが**オーケストレーター**である。オーケストレーターは設計と調査を自分で行い、実装とテストはSonnetのサブエージェントに委譲する。外部との受け渡しは全てオーケストレーターが行う。

## 役割分担

| 担当 | 実行者 | 責任範囲 |
|------|--------|----------|
| 調査・設計 | オーケストレーター（Opus） | コードベース調査、方針決定、作業指示書の作成、レビュー結果の集約、ユーザーとの対話 |
| 実装・テスト | `impl-worker`（Sonnet） | 指示書どおりのコード変更、テスト作成・実行、レビュー指摘の修正 |
| レビュー | 外部のレビュー手段、無ければ `impl-reviewer`（Sonnet） | 実装が受け入れ基準を満たすかの検証 |

**守るべき境界:**

- 実装エージェントは設計判断をしない。指示書にない判断が必要になったらオーケストレーターに差し戻す。
- 実装エージェントとレビュー担当は直接やりとりしない。全ての受け渡しはオーケストレーターを経由する。
- オーケストレーターは自分でコードを書かない。書きたくなったら、それは指示書が不十分だという合図である。

## Phase 0: オーケストレーターのモデル確認

セッションのモデルがOpusでない場合、設計品質がこのワークフローの前提を満たさない。ユーザーに以下を伝えて選ばせる。

- `/model opus` に切り替えてからやり直す（推奨）
- このまま現在のモデルで設計を進める

ユーザーが即答を求めていない限り、勝手に続行せず確認する。Opusであれば何も言わずPhase 1へ進む。

## Phase 1: 調査

作業対象を理解する。**この段階ではコードを一切変更しない。**

1. 依頼内容から、影響範囲になりうるディレクトリ・ファイルを特定する
2. 既存の実装パターン、命名規則、テストの置き方、使用ライブラリを読み取る
3. ビルド・テスト・lintのコマンドを設定ファイル（Makefile、package.json、pyproject.toml等）から特定する
4. CLAUDE.md やプロジェクト規約があれば読む
5. 調査範囲が広い場合は `Explore` エージェントに並列で探索させてよい（読み取り専用のため安全）

調査で分かったことのうち、**設計判断に効いた事実だけ**を後段に残す。ファイルの全文引用は残さない。

## Phase 2: 設計

以下を含む設計をまとめる。ここで曖昧さを潰しきることが、Sonnetへの引き継ぎ品質を決める。

- **やること / やらないこと** — スコープの境界を明示する
- **変更対象ファイル** — 新規作成・修正・削除の別を付けて列挙する
- **各ファイルで何をするか** — 関数名・クラス名レベルまで具体化する
- **受け入れ基準** — 「何が満たされたら完了か」を検証可能な形で書く
- **テスト方針** — 追加するテストケースと、実行すべきコマンド
- **判断が割れうる箇所** — 設計上の選択とその理由。実装側が勝手に変えてはいけない点

設計中に、ユーザーに聞かないと決められない事項が出たら `AskUserQuestion` で確認する。

## Phase 3: 承認ゲート（必須）

**ユーザーの承認なしにPhase 4へ進んではならない。**

プランモードにいる場合は `ExitPlanMode` で設計を提示して承認を得る。プランモードでない場合は設計サマリをユーザーに提示し、明示的な同意を得る。

ユーザーが修正を求めたらPhase 2に戻る。承認が得られてはじめて実装フェーズに入る。

## Phase 4: 実装への引き継ぎ

### 4-1. 作業指示書を書き出す

サブエージェントはこの会話の履歴を引き継がない。**指示書は単体で読んで実装できるだけの自己完結性を持たせる。**

指示書をスクラッチパッドディレクトリに `<タスク名>-handoff.md` として書き出す。以下の構成で書く。

```markdown
# 作業指示書: <タスク名>

## ゴール
<何を実現するか。1〜3文>

## 前提知識
<調査で分かった、実装に必要な事実。既存パターン、規約、依存関係>

## 変更対象
| ファイル | 種別 | 内容 |
|----------|------|------|
| path/to/file.ts | 修正 | <具体的に何をするか> |

## 受け入れ基準
- [ ] <検証可能な条件>

## テスト
- 追加するテストケース: <列挙>
- 実行コマンド: `<コマンド>`

## やらないこと
- <スコープ外の明示>

## 判断を変えてはいけない点
- <設計上の決定と理由>

## 迷ったら
指示書にない判断が必要になったら、実装せずに質問として報告すること。
```

### 4-2. 実装エージェントを起動する

`Agent` ツールで `subagent_type: "claude-dev-orchestration-ja:impl-worker"` を起動し、指示書のパスを渡す。この識別子で解決できない場合は、このセッションで提示されているエージェントタイプ一覧から `impl-worker` を含むものを探す。

このエージェントIDは**修正ループで再利用する**ため記録しておく。再依頼は `SendMessage` で同じエージェントに送り、実装時の文脈を保ったまま修正させる。

### 4-3. 実装結果を受け取る

実装エージェントの報告を確認する。以下がある場合はレビューに進まず先に解消する。

- 指示書にない判断を求める質問が返ってきた → 設計判断としてオーケストレーターが回答する（必要ならユーザーに確認する）
- テストが通っていない → 原因を確認し、実装エージェントに差し戻す
- 受け入れ基準の一部が未達 → 未達の理由を確認する

## Phase 5: レビュー

### 5-1. レビュー手段を選ぶ

以下の優先順位で決める。

1. **ユーザーが指定したレビュー手段** — 明示があればそれに従う
2. **利用可能な外部のレビュー用エージェント／スキル** — このセッションで実際に起動できるものに限る
3. **同梱の `impl-reviewer` エージェント** — 上記が無い場合

外部手段を探すときは、このセッションで提示されているエージェントタイプ一覧と、利用可能なスキル一覧からレビュー用途のものを拾う。判断に迷う場合や複数の候補がある場合はユーザーに確認する。

**候補に含めてはいけないもの:** ユーザーが自分で起動する必要があるコマンド（`/code-review` 等）。オーケストレーターからは起動できないため、レビュー手段として当てにしない。ユーザーにそれを使いたいか尋ねることは可能。

### 5-2. 外部手段に委譲する場合

外部エージェント・プラグインとのやりとりは**オーケストレーターが行う**。実装エージェントには触らせない。

渡すもの:

- 受け入れ基準（指示書から抜粋）
- 変更されたファイルの一覧
- 設計上の意図と、変更してはいけない判断

外部レビューの出力形式はこちらで制御できない。返ってきた内容を、5-4 の共通形式に**オーケストレーターが整形する**。

### 5-3. 同梱エージェントを使う場合

`Agent` ツールで `subagent_type: "claude-dev-orchestration-ja:impl-reviewer"` を起動し、指示書のパスと変更ファイル一覧を渡す。この識別子で解決できない場合は、エージェントタイプ一覧から `impl-reviewer` を含むものを探す。

### 5-4. レビュー結果の集約

レビュー元が何であれ、以下の形に揃えてから次に進む。

| 指摘 | 深刻度 | 該当箇所 | 対応方針 |
|------|--------|----------|----------|
| <内容> | 🔴致命 / 🟡要修正 / 🟢任意 | file:line | 修正する / 見送る（理由） |

🔴と🟡があればPhase 6へ。🟢のみ、または指摘なしならPhase 7へ。

## Phase 6: 修正ループ

**上限3周。** 周回数をカウントし、上限に達したら打ち切る。

1. 🔴・🟡の指摘を実装エージェントに `SendMessage` で差し戻す（Phase 4-2 で記録したID宛）
2. 修正完了の報告を受け取る
3. 同じレビュー手段で再レビューする
4. 🔴・🟡が残っていれば1に戻る

**打ち切り条件と、その時の扱い:**

- 3周しても🔴・🟡が残る → ループを止め、残っている指摘・修正の試行内容・オーケストレーターとしての評価をユーザーに報告し、判断を仰ぐ
- 同じ指摘が2周続けて解消しない → 実装の問題ではなく設計の問題である可能性が高い。ループを止めてPhase 2に戻るかをユーザーに確認する
- レビューの指摘が設計判断そのものを否定している → 実装エージェントに差し戻さず、オーケストレーターが設計の妥当性を評価してユーザーに報告する

## Phase 7: 完了報告

以下をユーザーに報告する。

- 実装した内容（変更ファイルと要点）
- 受け入れ基準の充足状況（各項目の達成／未達）
- テスト実行結果（実際の出力に基づく事実）
- レビュー結果と、見送った指摘があればその理由
- 残課題（あれば）

**テストが失敗している、受け入れ基準が未達、レビュー指摘が未解消のいずれかがある場合は、それを明示せずに完了と報告しない。**
