# 語彙パターン詳細（Layer 1）

AI生成文章に頻出する日本語の定型句・キラーワード・過剰カタカナ語のリスト。検出時はここを参照する。

## カテゴリ

1. 中身のない強調
2. 定型的な句
3. ヘッジ表現
4. 過剰なカタカナ語
5. 段落末の「きれいに閉じる」系
6. 導入の定型
7. 接続の常套句
8. 否定的対比（negative parallelism）
9. 漢語の過剰
10. 問いかけによる共感演出

各カテゴリの**棄却例**は「人間が正当に使う用法」であり、該当したら報告しない。
SKILL.md の「報告の共通基準」と併せて使う。

## 1. 中身のない強調

内容を具体的に語る代わりに評価語で埋めるパターン。Layer 4「平均回帰」にも関連。

- 包括的な
- 多面的な / 多角的な
- 革新的な / 画期的な
- 最適な / 最適化された
- 効率的な / 効率化
- 強力な
- 優れた
- 高度な
- 重要な役割を果たす
- 非常に重要
- きわめて重要
- 多くのメリット
- さまざまな利点
- 幅広い用途
- 劇的に改善
- 飛躍的に向上
- 大幅に
- 圧倒的な

**修正方向**: 何がどう「革新的」「強力」なのか具体化する。数値・比較対象・固有名詞で置き換える。

**棄却例**: 直後に具体的な根拠が続いている場合（「効率的だ。同じ処理が3回のAPI呼び出しから1回になる」）。
評価語そのものではなく、**評価語で具体を代替していること**が問題。

## 2. 定型的な句

記事構造を支えるだけで情報を持たない常套句。

### 動詞を含む定型
- 〜を活用することで
- 〜を利用することで
- 〜を実現することで
- 〜の可能性を秘めている
- 〜の可能性が広がる
- 〜に焦点を当てて
- 〜を紐解いていく
- 〜について解説する / します
- 〜について見ていく / 見ていきましょう
- 〜をご紹介する / します

### まとめ系
- まとめると
- 結論として
- 総じて
- 一言で言えば
- 要するに
- いかがでしたでしょうか

### 呼びかけ系（読者への過剰な配慮）
- ぜひ〜してみてください
- 〜することをおすすめします
- 〜してみましょう
- ぜひ参考にしてみてください

**修正方向**: ほとんど削除して良い。動作主や結果を具体的に書く。

## 3. ヘッジ表現

責任回避・断定回避の常套句。多用は避ける。

- 〜かもしれません
- 〜と考えられます
- 〜と思われます
- 〜と言えるでしょう
- 〜と言える
- 〜する可能性がある
- 一般的には
- 傾向がある
- 場合によっては
- ケースバイケース

**修正方向**: 断定できる場合は断定する。本当に不確実なら「自分は〜と思う」「自分の環境では〜だった」と主観を明示する。

**棄却例**: 本当に不確実な事柄に付いているヘッジ。未検証の推測、環境依存で断定できない挙動、
将来の見通しなど。**断定できることを断定していない場合だけ**報告する。
むしろ Layer 5 の観点では、根拠のない断定よりヘッジの方が正しいことがある。

## 4. 過剰なカタカナ語

日本語で表現できるのにカタカナで置き換えられている場合にフラグ。技術用語として定着しているもの（API、フレームワーク等）は対象外。

### 典型的な過剰カタカナ
- ソリューション → 解決策
- エコシステム → （多くの場合削除可能、または「周辺環境」）
- パラダイムシフト → 根本的な転換
- ゲームチェンジャー → 状況を変えるもの
- シナジー → 相乗効果
- イノベーション → 刷新 / 革新
- コミットメント → 約束 / 責任
- プライオリティ → 優先度
- スケーラビリティ → 拡張性
- フレキシビリティ → 柔軟性

**修正方向**: 技術文脈で定着している語（API, CLI, SDK, SaaS等）は残す。それ以外の抽象的カタカナは日本語に置き換えるか削除する。

## 5. 段落末の「きれいに閉じる」系

AIは段落を必ず何らかの締めで終わらせる癖がある。

- 以上が〜です / 以上がポイントです
- 以上のように〜
- このように〜
- 次に進みましょう
- 次は〜について見ていきます
- 最後にまとめます
- 〜していきましょう
- 〜が重要です
- 〜ですね

**修正方向**: 多くの場合、段落末の締め文は削っても意味が通る。削る。特に連続して出現する場合は必ず削る。

---

## 6. 導入の定型

記事や段落の冒頭に置かれる自己言及的な予告。

- 今回は〜について
- 本記事では〜を解説
- この記事では〜を紹介します
- まず〜から見ていきましょう
- ここでは〜について扱います
- 結論から言うと（続く内容が抽象的な場合のみ問題）

**修正方向**: 削除。見出しが十分な予告になっている。本文は即座に本題から始める。

---

## 7. 接続の常套句

### 順接（ほぼ削除可能）
- また
- さらに
- 加えて
- そして
- それに加えて

### 過剰な逆接・転換
- しかしながら（「しかし」で十分）
- 一方で（多用するとAIっぽい）
- とはいえ（多用するとAIっぽい）

### 説明導入
- ここで注目すべきは
- 注目すべき点は
- 特筆すべきは
- 興味深いことに

**修正方向**: 順接は9割削れる。削って文脈で繋がるなら削る。逆接は必要なときだけ使う。

**棄却例**: 削ると論理が繋がらなくなる接続詞。特に「しかし」「ただし」で本当に論旨が
反転している箇所。**削っても意味が通ることを確認してから**報告する。

## 8. 否定的対比（negative parallelism）

**AI文章の手がかりとして最も頻繁に指摘されるパターン。** 「XではなくY」の形で、
実際には新しい情報を足していないのに深遠に見せる。

### 検出パターン
- 「単なる〜ではなく、〜だ」
- 「重要なのは〜ではない。〜だ」
- 「問題は〜ではありません。問題は〜です」
- 「〜だからではなく、〜だから」
- 「これは〜ではない。〜なのだ」

### 見分け方（この判定が要）
第2節が、第1節で伏せられた情報を**新たに足しているか**を見る。

- 足している → **人間の正当な用法。棄却する**
- 同じ内容を語彙だけ豪華に言い直している → 報告（損失は「偽の対比」）

### 検出例
```
これは単なる高速化ではない。開発体験の革新である。
  → 「高速化」と「開発体験の革新」が何によって区別されるか書かれていない。報告。

これは高速化ではなく、キャッシュ層の追加によるレスポンス改善だ。
  → 第2節が具体的な機構を足している。棄却。
```

**修正方向**: 対比をやめて、後半だけを直接書く。「開発体験が変わる。ビルドを待つ間の
手戻りが無くなるからだ」のように、対比の代わりに理由を書く。

## 9. 漢語の過剰

漢語（漢字熟語）の密度が高いと翻訳調・機械調になる。カタカナ過剰より日本語らしさを損なう。

### 検出例
```
包括的視点から最適化された構成で網羅的な情報提供を実現する
  → 「全体を見て構成を整え、必要な情報を漏らさず載せる」
本手法の適用により処理効率の向上が期待される
  → 「この方法を使うと処理が速くなる」
```

### 検出シグナル
- 1文に4字熟語が3つ以上
- 「〜の実現」「〜の向上」「〜の最適化」など、動詞を名詞化した漢語が連続する
- 和語で言えることを漢語で言っている（「使う」→「利用する」→「活用を図る」）

**修正方向**: 動詞に戻す。「効率の向上を図る」→「速くする」。
名詞化した漢語を1文に1つまでに減らすだけで印象が大きく変わる。

**棄却例**: 学術論文、仕様書、法務文書など、漢語が文体として要求される文書。
技術用語として定着している熟語（「排他制御」「冪等性」など）。

## 10. 問いかけによる共感演出

読者に問いかけて共感を作ろうとするが、答えが自明で情報を持たない。

### 検出パターン
- 「〜ではないでしょうか」
- 「〜と思いませんか？」
- 「〜な経験はありませんか？」
- 「なぜでしょうか。それは〜だからです」（自問自答）

**修正方向**: 問いを消して断定に変える。「〜ではないでしょうか」→「〜だ」。
自問自答は問いを削り、答えだけ書く。

**棄却例**: 本当に読者に考えさせたい箇所（記事全体で1〜2回）。
答えが自明でない問い。導入で読者の状況を絞り込む問い。

---

## 検出時の注意

- すべての出現を列挙せず、**1記事内で2回以上出る場合**や、**パターンが重なって出る場合**を優先してフラグ
- 技術文書として適切なカタカナ語（API、MCP、CLI等）は検出対象外
- 引用やコード内の文字列は対象外
- **各パターンの棄却例に必ず照合する。** 語句が一致しただけでは報告しない
