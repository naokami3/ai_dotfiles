# 軸J: フロントエンド（React 18 + TypeScript）

対象シグナル: useState が多い / 状態同士が連動する / props バケツリレー / Context /
カスタムフック / 楽観更新 / ローディングとエラーの分岐 / API レスポンスの型がコンポーネントに露出

detect.rb の該当 signal: `use_state_per_component`, `prop_passthrough_components`

このファイルの項目はすべてスタブ（発火条件のみ）。実装例は必要になった時点で追記する。

## Custom Hook

発火条件: 1コンポーネント内の `useState` が3つ以上、または `useEffect` が2つ以上ある /
同じ状態＋副作用の組が2コンポーネント以上に複製されている。
適用しない条件: 状態が1つでコンポーネント内に閉じている。

## Reducer・State Machine

発火条件: 複数の `useState` が互いに整合を保つ必要がある（ローディング中かつエラー、のような
不正な組み合わせが型上表現できてしまう） / 状態遷移に規則がある。
適用しない条件: 状態が独立していて、同時に矛盾しない。

## Compound Component

発火条件: 1コンポーネントの props が8個以上、うち表示の出し分けフラグが3個以上ある /
利用側でレイアウトの差し替え要求が出ている。
適用しない条件: 利用箇所が1つで、props が固定。

## Provider（Context）

発火条件: 受け取った同名の prop をそのまま子へ渡しているコンポーネントが3つ以上ある（バケツリレー） /
アプリ全体で共有する値（認証ユーザー、テーマ、i18n）を2箇所以上で必要としている。
適用しない条件: 伝播が2階層以内、または頻繁に更新される値（再レンダリング範囲が広がる）。

## Adapter層（API クライアント）

発火条件: API のレスポンス型（snake_case、nullable、日付文字列）がコンポーネントに直接届いている /
同じエンドポイントの `fetch` が2箇所以上にある。
適用しない条件: 呼び出しが1箇所で、型がそのままドメインの型と一致している。

## Optimistic Update

発火条件: 更新の応答待ち時間がUI上の待機として現れており、失敗率が低く巻き戻し可能 /
「押した瞬間に反映してほしい」要求が明示されている。
適用しない条件: 失敗時に巻き戻せない（決済、確定操作）。

## Error・Suspense Boundary

発火条件: `isLoading` / `error` の分岐が3コンポーネント以上に複製されている /
1つの失敗が画面全体を落としている。
適用しない条件: 非同期処理が1箇所のみ。
