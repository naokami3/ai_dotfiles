# pattern-radar

観測可能なシグナルからデザインパターンの適用候補を逆引きし、候補・帰結・適用しない条件を並べる。
**採用するかどうかを決めるのはユーザーであり、このスキルではない。**

## 絶対規則

1. 索引は「シグナル → 候補パターン」の逆引きで使う。パターン名から入らない。
2. 発火条件は数えられる述語だけを使う。「複雑」「多い」「読みにくい」は発火条件にしない。
3. 候補を出すときは必ず「適用しない条件」に該当するかを照合し、結果を書く。
4. **コードを書き換えない。** 検出・提示までで止める。ユーザーが明示的に実装を指示した場合のみ実装に移る。
   Write / Edit は `<project>/.claude/decisions.md` の作成・追記にのみ使う。それ以外のファイルには使わない。
5. 指摘は必ず検出シグナルから始める。パターン名から始めない。
6. 該当軸の references のみを読む。10軸すべてを読み込まない。

## 手順

1. **対象を決める**
   - 引数 `review` → 未コミットの変更ファイル（`--diff` の既定。範囲は下の review モードを参照）
   - 引数 `<path>` → そのファイル / ディレクトリ
   - 引数なし → 会話に出ているファイル、貼られたコード、これから書こうとしている処理
2. **機械検出を先に走らせる**（Ruby / TSX ファイルが対象にある場合）
   ```bash
   ruby ${CLAUDE_SKILL_DIR}/scripts/detect.rb app/controllers/orders_controller.rb
   ruby ${CLAUDE_SKILL_DIR}/scripts/detect.rb --diff        # review 時
   ```
   出力は JSON Lines（`file` / `line` / `signal` / `count` / `threshold` / `axis`）。閾値未満は出力されない。

   実行時の制約（守らないと毎回許可を求めることになる）:
   - スクリプトの位置は**上の `${CLAUDE_SKILL_DIR}/scripts/detect.rb` の形のまま**指定する。
     対象リポジトリの中に同名のスクリプトが見えていても、そちらの相対パスで実行しない。
   - `cd` やパイプを前後に付けず、`ruby <script> <引数>` の形だけで実行する。
3. **コードの確認には Read / Grep / Glob ツールを使う**。`grep` `sed` `wc` `ls` `cat` を Bash で実行しない。
4. **会話由来のシグナルも軸に写像する**。ユーザーが口にした言葉（「規約同意のチェックボックス」「status を持たせたい」）は
   スクリプトでは拾えない。下のルーティング表で軸に変換する。
5. **該当軸の `references/axis-*.md` を読む**（通常1〜2ファイル）。発火条件と適用しない条件を照合する。
6. **出力フォーマットで提示する**。条件を満たす場合のみ AskUserQuestion で選択させる。

シグナルが1件も立たなければ「検出なし」と1行で答える。無理に候補を作らない。

## ルーティング表

この表は**ユーザーの言葉から軸を引くための索引**であり、発火判定そのものではない。
軸を特定したら references の数えられる条件で照合し、そこを満たさなければ候補を出さない。

| 軸 | 代表シグナル（ユーザーの言葉 / detect.rb の signal） | 参照先 |
|---|---|---|
| A 分岐の増殖 | when 節が3つ以上 / 仕様追加のたびに分岐が増える / status の値が3つ以上で遷移規則がある / 同一対象への nil 判定が3箇所以上（`case_when_branches`, `nil_checks_per_receiver`） | `references/axis-a-branching.md` |
| B 生成の複雑化 | コンストラクタの引数が5つ以上 / 生成する具象を選ぶ分岐が2箇所以上 / 同じテストデータ生成が3箇所以上 | `references/axis-b-construction.md` |
| C 境界と外部依存 | 外部SDKの型がドメイン層に露出 / 同一エンドポイントの呼び出しが2箇所以上 / SDKを直接呼びテストで差し替え点がない | `references/axis-c-boundary.md` |
| D 手続きの肥大 | 1アクションが21行以上 / 複数モデル横断のトランザクション＋外部I/O（`controller_action_lines`） | `references/axis-d-procedure.md` |
| E データアクセス | 条件を3つ以上組み合わせる where / 3条件以上を含む同一の where が2箇所以上 / group・join を含む集計 | `references/axis-e-data-access.md` |
| F 入力と表示 | 1リクエストで2モデル以上を保存 / DBカラムに無い入力項目 / `validates ... on:` / 表示専用メソッドが2つ以上 / helper の引数が3つ以上（`persistence_calls_per_method`, `validates_with_context`） | `references/axis-f-input-view.md` |
| G 値とドメイン | プリミティブが常に2つ以上セットで運ばれる / 同じ書式・比較ロジックが2箇所以上 / 権限判定の if がネスト / ロール分岐が2ファイル以上 | `references/axis-g-domain.md` |
| H 副作用と通知 | after_commit / after_save のブロックが5行以上 / 1つの出来事への後続処理が3つ以上（`callback_block_lines`） | `references/axis-h-side-effect.md` |
| I 横断関心 | 同じ before_action が3コントローラ以上 / 同じメソッド群が2モデル以上に複製 / Concern が200行超 | `references/axis-i-cross-cutting.md` |
| J フロントエンド | 1コンポーネントの useState が3つ以上 / 受け取った同名 prop を素通ししているコンポーネントが3つ以上 / props が8個以上 / `isLoading`・`error` の分岐が3コンポーネント以上（`use_state_per_component`, `prop_passthrough_components`） | `references/axis-j-frontend.md` |

`axis` が `F/D` のように複数返る場合は、両方の references を読んで候補を並べる。

## 出力フォーマット（固定・逸脱禁止）

検出ごとに次のブロックを出す。行の順序・ラベルを変えない。

**出力はフェンス付きコードブロックで囲む。** `帰結:` のインデントを保つためであり、
`&nbsp;` などの HTML エンティティや全角空白でインデントを作らない。

```
検出シグナル: <数えられる事実。ファイルと行を含む>
候補: A) <パターン名> B) <パターン名> C) 現状維持
帰結:
  A) 短期: <今回の変更直後に効くこと>
     長期: <仕様追加が重なったときの効き方>
     懸念: <腐るときの兆候・逆効果になる条件>
  B) 短期: / 長期: / 懸念:（同じ3行）
  C) 短期: / 長期: / 懸念:（同じ3行）
適用しない条件に該当するか: <該当有無と理由>
判断はユーザーに委ねる
```

例:

```
検出シグナル: app/controllers/orders_controller.rb:14 の create で save! が2回（Order と Shipment）
候補: A) Form Object B) Service(Command) C) 現状維持
帰結:
  A) 短期: 入力検証を1オブジェクトに集約でき、アクションは7行→3行
     長期: カラム外の入力項目が増えても影響がフォームに閉じる
     懸念: モデルとフォームでバリデーションが二重定義になりやすい
  B) 短期: トランザクション境界が1箇所に集まる
     長期: 通知・外部連携が増えても置き場所が決まっている
     懸念: モデルが貧血化する。Service が Service を呼ぶ階層が育つ
  C) 短期: 追加コストなし
     長期: 保存順序と検証の責任がアクションに残り、同種の画面ごとに複製される
     懸念: 片方の保存だけ成功する不整合が残り続ける
適用しない条件に該当するか: 該当しない（Shipment は Order のカラムに写像できない別テーブル）
判断はユーザーに委ねる
```

### 短期 / 長期 / 懸念 の書き方

すべて**対象コードの事実に接続して書く**。パターン一般の教科書的な説明を書かない。

- **短期**: この変更を入れた直後に観測できること。行数、触るファイル数、既存テストへの影響など
- **長期**: 「何が増えたときに」効くのかを条件付きで書く。増える見込みが読めないなら、その旨を書く
- **懸念**: references の「よくある過剰適用の兆候」と、対象コードの事実から書く。
  そのパターンが逆効果になる条件を1つは挙げる
- 現状維持にも3行とも書く。**現状維持の長期は「今の構造のまま何が増えるか」**であり、空欄にしない
- 書けない項目は無理に埋めず `不明（判断材料が足りない）` と書く。水増ししない

`review` モードのときだけ、検出の列挙より前に `対象範囲: <見た差分の範囲>` の1行を置く。
これがフォーマットで許される唯一の追加行で、検出ごとのブロックの中には入れない。

候補の数に関わらずラベルは `A)` から連番で振り、**最後の1つを必ず `現状維持` にする**。
適用候補が1つなら `候補: A) <パターン名> B) 現状維持`、3つなら `A) B) C) D) 現状維持` となる。
`帰結:` は候補と同じラベル・同じ数だけ並べ、**各候補に 短期 / 長期 / 懸念 の3行を必ず書く**。

## 質問ルール（AskUserQuestion）

次の**両方**を満たすときだけ AskUserQuestion を使う。満たさなければ出力フォーマットの提示だけで止める。

- **現状維持を除いた適用候補が2つ以上ある**（パターン候補が1つだけなら質問しない）
- 後戻りコストが高い（テーブル追加、公開インタフェース変更、複数ファイルの移動を伴う）

質問の作り方:

- 1回の質問は1論点。複数の検出をまとめて聞かない。
- 選択肢は相互排他にする。
- 各選択肢の description は「短期に効くこと」と「長期の懸念」を1行にまとめて書く。
- 「現状維持」を常に選択肢に含める。
- 推奨マーク（`（推奨）`）は根拠を明示できる場合のみ、先頭の選択肢に付ける。根拠が書けないなら付けない。

### 回答後の記録

ユーザーが回答したら、`<project>/.claude/decisions.md` に1行追記する（ファイルが無ければ作成する）。

```
- YYYY-MM-DD | <対象ファイル/境界> | <採用> | <理由>
```

例: `- 2026-07-27 | app/controllers/orders_controller.rb#create | Form Object | 規約同意がカラムに無く、Order と Shipment を同時保存するため`

### 再質問の抑止

質問の前に `<project>/.claude/decisions.md` を読む。同じ対象（ファイル / 境界）について既存の記録があれば、
**再質問せずその決定に従う**。決定と異なる提案をする場合は、記録を引用したうえで「前回の決定を覆す理由」を明示する。

## review モード

引数 `review` が渡された場合:

1. `ruby ${CLAUDE_SKILL_DIR}/scripts/detect.rb --diff` を実行する。
   対象は**未ステージ変更 ＋ ステージ済み変更 ＋ 未追跡ファイル**（`--diff` の既定）。
   ブランチ全体をレビューする場合は基準を明示して `--diff <base>`（`git diff --name-only <base>...HEAD`）を使う。
   どの範囲を見たかを出力の冒頭に1行で書く。
2. `git diff`（または指定した基準との差分）の**変更範囲**に対して同じ判定を行う。
   変更されていない既存コードの検出は報告しない。未追跡ファイルは全体が変更範囲となる。
3. 検出ごとに出力フォーマットで指摘する。レビューでは AskUserQuestion を使わず、提示のみで止める。
4. `decisions.md` に記録済みの対象は、その決定に沿っているかだけを確認する。決定と一致していれば指摘しない。

## スコープ外

- コードの自動修正・リファクタリングの実行
- 命名、フォーマット、テストの有無など構造選択と無関係な指摘
- パターンの一般的な解説（ユーザーが明示的に求めた場合を除く）
