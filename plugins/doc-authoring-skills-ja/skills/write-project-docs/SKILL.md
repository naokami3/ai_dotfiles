# プロジェクトドキュメント作成ガイド

## 関連スキルの使い分け

| 対象 | スキル |
|---|---|
| architecture.md / roadmap.md 等の docs/ 配下 | `write-project-docs`（本スキル） |
| 人間向け HTML 資料（概観・詳細仕様・図） | `write-html-docs` |
| 技術的な意思決定の記録 | `write-adr` |
| AGENTS.md / CLAUDE.md | `write-agent-instructions` |
| 作成・更新後の検証 | `review-docs` |

## ドキュメントの役割分担

| ファイル | 対象者 | 内容 | 更新頻度 |
|---------|--------|------|---------|
| AGENTS.md（+ CLAUDE.md ブリッジ） | コーディングエージェント | コマンド、ルール、落とし穴 | 機能追加時 |
| README.md | 全員 | プロジェクト概要、セットアップ | リリース時 |
| CONTRIBUTING.md | コントリビューター | 開発環境、規約、PR プロセス | 開発環境変更時 |
| docs/architecture.md | 開発者 | ディレクトリ構造、設計原則、Protocol | アーキテクチャ変更時 |
| docs/roadmap.md | 全員 | フェーズ、TODO、完了状況 | 機能完了時 |
| docs/security-design.md | 開発者・監査者 | 脅威モデル、APIキー管理、通信先 | セキュリティ設計変更時 |
| docs/adr/ | 開発者 | 技術的意思決定の記録 | 重要な判断時 |
| llms.txt（公開ドキュメントサイトがある場合） | エージェント | 主要ドキュメントへの地図 | 構成変更時 |
| docs/ の HTML 資料（**オプション**） | 人間 | 図付き概観・詳細仕様の HTML 版。md 正典からの生成物。作る場合は `write-html-docs` に従う | md 正典の変更時（再生成） |

## 読者にエージェントが含まれる

ドキュメントは人間だけでなくコーディングエージェントにも読まれる。エージェントは概観よりも、**具体的な答えへの最短経路**を必要とする。

- 見出しで内容が判別できること（「その他」「補足」のような見出しを避ける）
- 手順にはコピペ可能なコマンドを添えること
- 一次情報の置き場所を1箇所に決め、他からはリンクすること（同じ事実が2箇所にあると、片方が古くなったとき判別できない）
- 公開ドキュメントサイトを持つ場合は、主要ページの地図として `llms.txt`（H1・1〜3文の概要・リンク一覧からなる Markdown）を置く
- 長い参照文書（仕様・プロトコル等）の冒頭に「**この文書で分かること**」ブロックを置く
  （5 bullet 以内・その文書が答えられる質問の列挙のみ。事実を重複記述しない）。エージェントの
  「読む / 読まない」の判断を速くする

## 各ドキュメントの書き方

### architecture.md

1. ディレクトリ構造をツリー形式で記述（各ファイルに1行コメント）
2. 設計原則を箇条書きで明記
3. Protocol/Interface のコード例を含める
4. 既知の制約（DLL 競合、ライセンス等）を専用セクションで記述
5. **実装と乖離したら即座に更新する** — 嘘のドキュメントは害

### roadmap.md

1. フェーズごとにチェックボックスで進捗管理
2. 完了したフェーズには ✅ マーク
3. 各項目に補足（使用技術、ADR 参照等）を添える
4. 「将来の検討事項」で未確定の項目を分離

### security-design.md

1. 脅威モデルを最初に明記（何を守り、何を守らないか）
2. リスクレベルを正直に記述（過剰な安全性の主張を避ける）
3. APIキー、通信先、暗号化方式を表形式で整理
4. 「透明なセキュリティ」— 限界も文書化する

### CONTRIBUTING.md

1. 開発環境セットアップ手順（コピペで動くこと）
2. OS 固有の手順（Windows OCR 言語パック等）は別セクションで
3. コーディング規約はツール名とコマンドを明記
4. PR プロセスとレビュー基準

## 共通原則

- **DRY**: 同じ情報を複数ドキュメントに書かない。リンクで参照する
- **実装と同期**: コード変更時にドキュメントも更新する。コミットに含める
- **読者を意識**: 「誰が」「いつ」読むかを考えて書く
- **具体的に**: 「適切に設定する」ではなく「`keyring.set_password("grabtl", engine, key)` で保存する」
- **推測を書かない**: 確認していない挙動・数値を断定しない。未確認なら「未確認」と書く

## 大きくなったドキュメントを分割するとき

数百行を超えて一覧性を失ったドキュメントは、話題別のファイル群 + 索引へ分割する。
分割は「内容の移動」であり書き直しではない。次の手順で逸失と参照切れを機械的に防ぐ。

1. **行範囲の機械的コピーで分割する**（書き直しながら分割しない）。分割スクリプトに
   「全本文行がいずれかの分割先にコピーされたか」の**カバレッジ検証**を組み込む
2. 元ファイルは削除せず、**旧見出しを互換アンカーとして残す索引**に置換する
   （`ファイル.md#アンカー` 形式の既存リンク・外部リンクを壊さないため。各旧見出しの直下に
   分割先への移動案内リンクを置く）
3. 節名の文中参照（「〜」節・`ファイル名` の節名指し）をリポジトリ全体から grep で洗い出し、
   分割先への直リンクに更新する。一括置換は**期待出現回数を検証しながら**機械適用する
4. 分割先ファイル内の相対リンク（`../` の深さ変化）と、分割ファイル間の相互参照を更新する
5. 最後にリンク・アンカーの全数検証（`review-docs` の `scripts/check-doc-links.py`）を通す

## 実測記録・正典・橋渡しの 3 層分離

外部システムの挙動に依存するプロジェクトでは、次の 3 層を別ファイルに分けると更新責任が明確になる。

| 層 | 内容 | 更新のトリガ |
|---|---|---|
| 実測記録 | 生データ・再現手順・検証環境・「未確認」の明示 | 実測したとき |
| 正典（仕様） | 対処の契約・不変条件・終了コード | 実装を変えたとき |
| 橋渡しマップ | 「実挙動 → 対処」の対応表。**一次情報は持たず両者へリンク** | どちらかが変わったとき |

橋渡しマップに事実を書き始めると 3 箇所目の一次情報が生まれ、乖離の温床になる。
リンクと 1 行要約に徹する。

## 複数ドキュメントを更新するとき

1つの変更が複数ドキュメントに波及することが多い。着手前にチェックリストを作り、進捗を追う。

```
更新対象:
- [ ] docs/architecture.md — ディレクトリ構造の変更を反映
- [ ] README.md — セットアップ手順のコマンド変更を反映
- [ ] docs/roadmap.md — フェーズ2完了をチェック
- [ ] 相互リンクの整合性を確認
- [ ] review-docs で検証
```

漏れやすいのは、**変更したドキュメントを参照している側**。更新したファイル名でリポジトリ全体を検索し、リンク元も確認する。

## 完了条件

作成・更新後、**`review-docs` の基準で検証する。** must-fix 相当の指摘があれば修正してから完了報告する。
