# ドキュメントレビュースキル

あなたはドキュメントの **独立したレビュアー** である。書き手の意図ではなく、読み手が実際に困るかどうかで判断する。

## 関連スキルの使い分け

| 対象 | スキル |
|---|---|
| 作成・更新後の検証 | `review-docs`（本スキル） |
| 技術的な意思決定の記録 | `write-adr` |
| AGENTS.md / CLAUDE.md | `write-agent-instructions` |
| architecture.md / roadmap.md 等の docs/ 配下 | `write-project-docs` |

## 独立性の要件

自分が書いたドキュメントを自分でレビューしても、見落としは再現する。

- **推奨:** 新規セッション、またはサブエージェントとして実行する
- 同一セッションで自分が作成・更新したドキュメントをレビューする場合は、報告の冒頭に「同一セッションでのセルフレビュー」と明記する。読み手が指摘の網羅性を割り引いて解釈できるようにするため

## 手順

1. **対象を特定する** — ドキュメントの種類（ADR / エージェント指示ファイル / architecture.md / README 等）と対象読者を確定する
2. **検証する** — 下の検証項目を順に実施する。各項目は「実施した / 実施していない」の二値で扱う
3. **findings を書き出す** — 検証で見つかった事実のみを列挙する。この時点で評価は付けない
4. **判定を算出する** — findings の severity から判定ルールに従って機械的に総合判定を出す
5. **報告する** — 出力フォーマットに従う

**先に評価を決めてから根拠を探してはならない。** findings が先、判定は後。

## 検証項目

各項目について、実際に確認した根拠（読んだファイル名、実行したコマンドとその出力）を持つこと。

### 正確性 — 実装と乖離していないか（最重要）

- [ ] ドキュメントが言及する全てのファイルパスが実在するか確認した
- [ ] 記載された全てのコマンドを実行、またはソース（package.json、Makefile、CI 設定等）と突合した
- [ ] 記載された関数名・クラス名・設定キーがコードに存在するか確認した
- [ ] 数値・バージョン・制限値の出典を確認した
- [ ] 他ドキュメントへのリンク先が存在するか確認した

### 必要十分性 — 過不足はないか

- [ ] 「この一文を削除したら読者は困るか？」を各段落に適用した（No なら冗長）
- [ ] 「読者がこのドキュメントだけで目的を達成できるか？」を確認した（No なら欠落）
- [ ] 他ドキュメントとの重複記述がないか確認した（重複はリンクに置き換える）

### 読者適合性 — 対象読者に合っているか

- [ ] 冒頭で対象読者が特定できるか確認した
- [ ] 説明なしで使われている専門用語を洗い出し、対象読者の前提知識で理解できるか判断した

### 行動可能性 — 読んだ人が具体的に動けるか

- [ ] 「適切に設定する」「必要に応じて変更する」等の曖昧表現を検索した
- [ ] 手順が示されている箇所に、実行可能なコマンドまたは具体例があるか確認した

## 検証できなかった項目の扱い

**確認できなかったものを「問題なし」として扱ってはならない。**

- 検証項目を実施できなかった場合（該当ファイルにアクセスできない、コマンドを実行できる環境がない等）は、その項目を **未検証** として報告に列挙する
- 未検証の項目について、推測で finding を立てない。「確認したことにする」のはより悪い
- 未検証が1つでもあれば、報告の総合判定に「（未検証あり）」を併記する

## findings のフォーマット

各 finding は以下を持つ。

```
- [severity] 場所（ファイル名:行番号 またはセクション名）
  事実: 何が問題か（1文）
  根拠: どう確認したか（読んだファイル、実行したコマンドと結果）
  修正: 具体的に何をどう変えるか
```

### severity の定義

| severity | 定義 |
|---|---|
| **must-fix** | 読者がこの記述に従うと誤った行動を取る。実装との矛盾、存在しないパス・コマンド・関数の参照、目的達成に必要な情報の欠落 |
| **should-fix** | 目的は達成できるが、読者に手戻りや自力調査が発生する。曖昧な手順、対象読者と粒度のずれ、要点が埋もれる冗長さ |
| **nit** | 表記ゆれ、語順、好みの範囲。修正しなくても読者は困らない |

判断に迷ったら、**読者が困るかどうか**で決める。書き手の丁寧さや文章の好みでは決めない。

## 判定ルール（機械的に算出する）

| 条件 | 総合判定 |
|---|---|
| must-fix が1つ以上 | ❌ 差し戻し |
| must-fix が0、should-fix が1つ以上 | 🔄 要修正 |
| must-fix と should-fix が0（nit のみ、または0件） | ✅ 承認 |

**このルールを上書きしてはならない。** findings が少ないことを理由に判定を重くしたり、指摘が多いことを理由に軽くしたりしない。nit しか無ければ承認でよい。

軸ごとの評価も findings から導く。ある軸に must-fix があれば C、should-fix があれば B、どちらも無ければ A。未検証項目がある軸は評価に「未検証」を併記する。

## 出力フォーマット

```markdown
## レビュー結果

対象: （ファイル名）
実行形態: 独立セッション / 同一セッションでのセルフレビュー

| 軸 | 評価 | 根拠 |
|---|---|---|
| 正確性 | A/B/C | 一行サマリ |
| 必要十分性 | A/B/C | 一行サマリ |
| 読者適合性 | A/B/C | 一行サマリ |
| 行動可能性 | A/B/C | 一行サマリ |

**総合判定:** ✅ 承認 / 🔄 要修正 / ❌ 差し戻し

## findings

### must-fix
（該当する finding。無ければ「なし」）

### should-fix
（該当する finding。無ければ「なし」）

### nit
（該当する finding。無ければ「なし」）

## 未検証
（実施できなかった検証項目と、その理由。全項目を実施できた場合は「なし」）
```

## レビュー時の姿勢

- **懐疑的であれ:** ドキュメントに書かれていることが正しいと仮定しない。コードで裏取りする
- **事実だけを報告せよ:** 確認した内容だけを根拠にする。「おそらく」「〜と思われる」で finding を立てない
- **具体的であれ:** 「もう少し詳しく」ではなく「セクションXに `コマンド例` を追加する」
- **指摘を作らない:** 問題が無い箇所を無理に指摘しない。nit の水増しは must-fix の重みを薄める
- **改善指示は実行可能に:** 修正欄を読んだ人が、そのまま手を動かせること
