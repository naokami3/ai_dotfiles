# ADR 作成ガイド

技術的な意思決定を `docs/adr/NNNN-<slug>.md` に記録する。

## 関連スキルの使い分け

| 対象 | スキル |
|---|---|
| 技術的な意思決定の記録 | `write-adr`（本スキル） |
| AGENTS.md / CLAUDE.md | `write-agent-instructions` |
| architecture.md / roadmap.md 等の docs/ 配下 | `write-project-docs` |
| 作成後の検証 | `review-docs` |

## ADR の目的

ADR には2つの目的がある:

1. **記録**: 数ヶ月・数年後でも「なぜそう作ったか」を理解できるようにする
2. **思考整理と合意形成**: 書く過程で異なる見解が浮かび上がり、議論・解消の機会となる

## いつ ADR を書くか

- ライブラリ・フレームワーク・エンジンの選定・不採用を決めたとき
- アーキテクチャパターンを変更したとき（デコレータ導入、HTTP クライアント変更等）
- データベース・ストレージ・認証方式を選択したとき
- API 設計やテスト戦略の方針を決めたとき
- linter/formatter の警告への対処方針やライセンス互換性の判断をしたとき
- 「なぜこうしたのか」を将来の開発者が疑問に思いそうなとき

## 決定は人間のもの

ADR は「人間が下した意思決定の記録」であり、エージェントの提案書ではない。次の3点を守る。

1. **Decision と Confidence を代わりに決めない。** 会話・差分・コードから確定できない場合は、ADR を書く前にユーザーに確認する。「どちらでも良さそうなので A にしました」は記録の捏造にあたる
2. **実測していない値を Evaluation に書かない。** ベンチマーク、バンドルサイズ、メモリ使用量は、実際に測定またはソースを確認した値のみを記載し、出典を添える。測っていない場合は「未測定」と明記する
3. **検討していない選択肢を Candidates に並べない。** 実際に調査した選択肢だけを書く。列挙の見栄えのために候補を追加しない

未確定の項目を空欄で残すのは、もっともらしい値で埋めるより望ましい。

## フォーマット

**逆ピラミッド構造**で書く — 最も重要な結論を冒頭に、詳細は後半に配置する。

```markdown
# ADR-NNNN: タイトル

- **Status:** Proposed | Accepted | Superseded | Deprecated
- **Date:** YYYY-MM-DD
- **Decision makers:** @username
- **Confidence:** High | Medium | Low（この判断に対する確信度）

## Decision

**何を選んだか。** 理由の要約を1-2文で。

## Context

なぜこの判断が必要になったか。問題や背景を記述。

## Candidates（検討した選択肢がある場合）

### A. 選択肢A
- 特徴、メリット、デメリット

### B. 選択肢B
- 特徴、メリット、デメリット

## Evaluation（実測データがある場合）

実際に試した結果。コード例、ベンチマーク、品質比較など。
数値には出典（測定方法・測定日・参照ソース）を添える。

## Consequences

この判断の結果、何が変わるか。
- 良い影響
- トレードオフ
- 将来の課題

## Re-evaluation Triggers

以下の状況が発生した場合、この決定を再検討する:
- （この決定の前提が崩れる具体的な文脈変化を列挙）
```

## 書き方の原則

- **逆ピラミッド**: 結論を冒頭に。詳細を読まなくても判断内容がわかるようにする
- **判断の根拠を残す**: 「X を不採用にした」だけでなく「X を試したが Y の理由で不採用」
- **実測データを含む**: 可能な限りベンチマーク、品質比較、メモリ使用量の実測値を記録し、出典を添える
- **不採用理由も記録**: 将来同じ選択肢が提案されたときに再調査を避ける
- **信頼度を明示**: 確信を持って決めたのか、暫定的な判断なのかを Confidence で示す
- **再評価条件を書く**: どんな文脈変化があればこの判断を見直すべきかを明記する
- **簡潔に**: 1ページ以内に収める。補足資料はリンクで参照し、本文に詰め込まない

## ステータスの運用

| ステータス | 意味 |
|---|---|
| Proposed | 提案中。レビュー・議論を待っている段階 |
| Accepted | チームに受け入れられ、有効な決定 |
| Superseded | 新しい ADR に置き換えられた（置き換え先の ADR 番号をリンクすること） |
| Deprecated | 対象の仕組みが廃止され、もはや適用されない |

## 作成手順

1. **Decision・Confidence・Decision makers を確定する。** 会話から確定できなければユーザーに確認する
2. **採番する。** スキルに同梱の `scripts/next-adr-number.sh` を実行する。ディレクトリが無ければ作成して `0001` を返す

   ```bash
   scripts/next-adr-number.sh          # docs/adr を対象に次の番号を出力
   scripts/next-adr-number.sh path/to/adr   # ディレクトリを指定する場合
   ```

   スクリプトを実行できない環境では、`docs/adr/` の既存ファイル名から4桁の最大値を読み、+1 してゼロパディング4桁で採番する
3. `docs/adr/NNNN-<slug>.md` を作成し、上記テンプレートに値を埋めて保存する
4. Status は `Proposed` で初期化する（ユーザーが既に合意済みと明示した場合のみ `Accepted`）
5. **`review-docs` の基準で検証する。** must-fix 相当の指摘があれば修正してから完了報告する

## 記入例

```markdown
# ADR-0003: HTTP クライアントを axios から ky に変更

- **Status:** Accepted
- **Date:** 2026-03-15
- **Decision makers:** @naokami3
- **Confidence:** High

## Decision

**axios を廃止し ky を採用する。** バンドルサイズが 1/10 以下で、fetch ベースのため Node.js・ブラウザ双方で動作し、プロジェクトの軽量化方針に合致するため。

## Context

フロントエンドのバンドルサイズ削減が求められており、依存ライブラリの見直しを行った。axios は多機能だがバンドルサイズが大きく、現プロジェクトでは基本的な GET/POST のみを使用していた。

## Candidates

### A. ky
- fetch ベースのラッパー。リトライ・タイムアウト内蔵

### B. ofetch
- Nuxt エコシステム由来。機能は十分だがコミュニティが小さい

### C. 素の fetch
- 追加依存なし。ただしリトライ・タイムアウトを自前実装する必要がある

## Evaluation

`npm run build` 後の min+gzip サイズを実測（2026-03-15、Vite 5 / 本番ビルド）:

| ライブラリ | サイズ |
|---|---|
| axios | 29.1 kB |
| ky | 2.5 kB |
| ofetch | 3.1 kB |

素の fetch は未測定（追加依存が無いため 0 kB だが、自前実装分は未計測）。

## Consequences

- バンドルサイズが約 27 kB 削減される
- axios 固有の機能（interceptors）は ky の hooks で代替が必要
- 既存の API クライアント層を書き換える作業が発生する

## Re-evaluation Triggers

- ky のメンテナンスが停滞した場合（6ヶ月以上リリースなし）
- サーバーサイドで axios 固有機能（proxy 対応等）が必要になった場合
```
