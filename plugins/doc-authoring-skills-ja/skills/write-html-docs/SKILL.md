# 人間向け HTML 資料の作成ガイド

## 関連スキルの使い分け

| 対象 | スキル |
|---|---|
| 人間向け HTML 資料（概観・詳細仕様・図） | `write-html-docs`（本スキル） |
| architecture.md / roadmap.md 等の docs/ 配下（md） | `write-project-docs` |
| 技術的な意思決定の記録 | `write-adr` |
| AGENTS.md / CLAUDE.md | `write-agent-instructions` |
| 作成・更新後の検証 | `review-docs` |

## 前提: 二層構成の原則

HTML 資料を作る場合、ドキュメントは**二層構成**にする。

- **正典は常に md（エージェント向け）**。事実の一次情報・契約・仕様は md が持つ。
- **HTML は人間向けのレンダリング**。詳細仕様の HTML 版は md からの**生成物**とし、手書きの
  二重管理をしない（手書きすると必ず乖離する）。
- 手書きを許すのは**図が本体の解説ページ**（概観・対比図・フロー図など、対応する md 正典を
  持たないページ）だけ。その場合も事実の詳細は必ず md へリンクで誘導し、複製しない。
- `llms.txt` に「人間 = HTML / エージェント = md」の役割分担を明記する。
- HTML と md の記述が食い違ったら正典（md）が正しい。HTML 側にその旨のフッターを置く。

## 成果物の構成パターン

```
docs/
├── overview.html   # 図付き概観（手書き可）。全体像 + 詳細へのリンクハブ
├── <topic>.html    # 図が本体の解説ページ（手書き可・必要なら）
└── spec/           # 詳細仕様の HTML 版（md 正典から機械生成。手書き禁止）
    ├── index.html  # 目次 + 読む順ガイド
    └── <topic>.html
```

各生成ページには「本ページは <正典パス> から自動生成。修正は md 側で行い再生成すること」の
注記と、正典 md への直リンクを必ず置く。

## 生成器を自作する場合の要件（fail closed チェックリスト）

外部ライブラリを足さず、リポジトリの既存ランタイム（例: python3 標準ライブラリ）で書く。
以下を満たさない生成器は、壊れた・危険な HTML を黙って出力する。

- [ ] **対応する md 構文を対象ファイルの棚卸しで限定**した（使われていない構文は対応しない）
- [ ] 処理できない入力は黙って通さず**エラー列挙 + 非ゼロ終了**する。条件は機械判定可能に具体化する
      （例: 未閉鎖フェンス / 表セパレータ欠落 / リンク閉じ括弧欠落 / 不採用構文の混入）
- [ ] **コンテキスト別エスケープ**: テキストノード（`& < >`）/ 属性値（+ 引用符）/ コード
      （記法を解釈しない）。トークナイズしてから各片をエスケープし、二重エスケープを構造的に防ぐ
- [ ] **href の allowlist**: スキームなしの相対パスと `https://` のみ許可。`javascript:` 等の
      危険スキーム・`http:`・スキーム相対（`//`）・絶対パス・バックスラッシュ・正規化後に
      リポジトリ外へ出るパスはすべて拒否
- [ ] **GitHub 互換の見出しアンカー id** を生成する（md の `#アンカー` 付きリンクが HTML でも機能する）
- [ ] **リンク再計算規則**を持つ（生成先ディレクトリ基点への相対パス再計算。生成対象同士は .html へ）
- [ ] 出力は**決定的**（タイムスタンプ・乱数を含まない。同一入力 → バイト同一の出力）
- [ ] **単体テストを同時に書く**（各構文の変換・エスケープ・href 拒否の攻撃ケース・fail 条件・決定性）

## 生成物の同期（乖離を構造的に防ぐ）

- 生成物（HTML）はコミットする（閲覧者にビルドを要求しない）。
- 検証ゲート（pre-commit / CI / verify スクリプト）に**非変更型の最新性検査**を組み込む:
  一時ディレクトリ（mktemp）へ再生成して、コミット済み生成物とファイル集合の一致 + `cmp` で
  照合する。**検査は作業ツリーへ一切書き込まない**（「再生成して git diff」方式は検証自体が
  ツリーを書き換えるので使わない）。
- リポジトリに「中間ファイルを生成しない」等の規則がある場合、**生成物を例外として規則側に
  明記**する（CLAUDE.md・CONTRIBUTING 等、規則を記載している全箇所）。明記しないと
  独立レビューで規則違反として差し戻される。

## 図の作成基準

- **図は事実を主張する。** 図中のコマンド名・終了コード・手順の順序・状態遷移・数値はすべて
  正典・実装との突き合わせ対象になる（`review-docs` 参照）。飾りではなく仕様の別表現として書く。
- インライン SVG で自己完結させる（外部画像・CDN・スクリプトに依存しない）。
- 各 SVG に `role="img"` と `<title>`（図の説明文）を付ける。色のみに依存した表現をしない
  （ラベル・実線/点線を併用する）。
- ライト/ダーク両対応: 配色は CSS 変数 + `prefers-color-scheme` で切り替える。SVG の
  `fill`/`stroke` も `var(--…)` を使う。
- **生成ページに図を足すときは生成物を直接編集しない**（最新性検査が壊れる）。生成器に
  図フラグメントの注入機構を持たせる（例: `<slug>--<見出しアンカー>--NN.html` の命名で
  該当見出し直後へ挿入）。フラグメントは生 HTML として注入されるため、**要素・属性の明示
  allowlist で検証**する（`on*` 属性・`style` 属性・`script`/`foreignObject` 等の拒否、
  `url()` は同一文書内参照 `url(#id)` のみ、href は本文と同一規則）。
- 手書きページ・生成ページ・フラグメントで同一の CSS クラス体系（box / arrow / label 等）を
  共有し、見た目を統一する。

## 検証（完了条件）

作成・更新後、次をすべて実施してから `review-docs` の独立レビューにかける。

1. **リンク・アンカーの全数機械検証** — `review-docs` 同梱の `scripts/check-doc-links.py` を使う
   （md / HTML 双方の相対リンク解決とアンカー実在を照合する）。
2. **タグ整合の機械検証** — `html.parser` 等での開閉タグ照合。
3. **実表示確認（ライト/ダーク両方）** — ヘッドレスブラウザで全ページを撮影し、図のはみ出し・
   重なり・可読性を目視する。注意: ヘッドレス Chrome は **OS のダークモード設定を継承する**。
   ライト表示を強制するには `prefers-color-scheme: dark` のメディアクエリを無効化した一時コピー
   （例: `min-width: 99999px` へ sed 置換）を撮影する。
4. `review-docs` による独立レビュー — 図中の事実主張の突き合わせを検証範囲に含めること。
   must-fix 相当があれば修正してから完了報告する。
