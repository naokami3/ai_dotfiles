# システム機能一覧の作成

このスキルを起動したセッションが**進行役**である。
このスキルの範囲は **1つのシステムを単体で把握すること**に限る。他システムとの比較・対応付けは行わない。

## 原則: 読むべき全件をスクリプトで数え、エージェントは小さく分けて読み、書いた内容はスクリプトで確かめる

全コードを1つのエージェントに読ませると、コンテキストが溢れて詳細が落ち、記憶や名前からの推測で
機能を書く（ハルシネーション）。これを次の仕組みで防ぐ。

| 起きること | 防ぎ方 | スクリプトで保証できる範囲 |
|---|---|---|
| 記憶で書く | 数千行の担当範囲ごとに新しいサブエージェントが読む。進行役はコードを読まない | — |
| 漏れに気づけない | スクリプトで作った全ファイル・全エントリーポイントの一覧と照合し、網羅率を数値で出す | 一覧内の網羅。除外したファイルのエントリーポイント候補は警告する |
| 読まずに書く | スクリプトが無作為に選んだ区間から1行ずつ引用させる（読了確認） | 指定区間の実在行を答えたこと |
| 名前から推測する | すべての主張に `ファイル:行` と引用を付けさせ、その行に実在するか照合する | 引用文字列の実在（意味の正しさではない） |
| 権限・制約を盛る | 利用者・制約は1件ずつ根拠行の番号を必須にする | 根拠行が示されていること |
| 集約で話を盛る | 集約で書けるのは名前・グループ分け・利用者表記の写像だけ。単独の機能は集約前の要約をそのまま使う | エントリーポイント・データ・根拠・制約・確信度は改変不可 |
| 意味の誤り・対象外への逃がし | 別エージェントがリスク順の抜き取りで機能と「対象外のエントリーポイント」をコードと照合する | 抜き取りの範囲のみ（統計的） |

**意味の正しさはスクリプトでは保証できない。** 独立検証の結果（誤り率）と、確信度・要確認事項を成果物に必ず残す。

**進行役の境界:**

- 自分で対象システムのコードを読まない（Phase 0 の構成把握と検出ルールの作成時を除く）
- 抽出 JSON を自分で読まない（Phase 1 の試行の品質確認を除く）。スクリプトの要約出力と `digest.txt` だけで判断する
- エントリーポイントを手で列挙しない。必ず検出ルールを実行した結果を使う

## 用語

| 用語 | 意味 |
|---|---|
| エントリーポイント | 外から機能を呼び出せる箇所（API・画面の URL・ジョブ・CLI・テーブルなど） |
| ファイル一覧・エントリーポイント一覧 | 漏れなく読むべき全件。スクリプトが作り、網羅率はこれに対して数える |
| 検出ルール | エントリーポイントを見つける正規表現（`detectors/*.yaml`） |
| 担当範囲 | 1体の抽出担当が読むコードのまとまり（数千行）。ファイル名・キー名・引数では `slice` と書く。ID は `S` + 6桁 |
| 指示書 | 担当範囲ごとにスクリプトが作る抽出担当への指示（`briefs/<S>.md`） |
| 根拠 | `ファイル:行` とその行の文字列の引用 |
| 読了確認 | スクリプトが無作為に選んだ行の内容を答えさせ、読んだことを確かめる仕組み |
| 抜粋読み | テスト名・定義の行だけを読む読み方（既定ではテストが対象） |
| 集約前の機能 | 担当範囲ごとに抽出した機能（ID は `<S>-F<番号>`）。集約で1つの機能にまとめられる |
| 進行役 | このスキルを起動したセッション（あなた） |
| 試行 | 本実行の前に数個の担当範囲だけで実行し、トークン量を実測すること |

## 役割分担

| 担当 | 実行者 | 責任 |
|---|---|---|
| 進行・判断・グループ分け | 進行役 | 各 Phase の実行、ユーザーとの対話、grouping.json の作成 |
| 抽出 | `inventory-extractor`（Sonnet、Read/Write のみ） | 1つの担当範囲を読み extract/<S>.json を書く |
| 独立検証 | `inventory-verifier`（Sonnet） | 抜き取りの機能・対象外のエントリーポイントをコードと照合し review/<batch>.json を書く |
| 列挙・分割・検証・集約・出力 | 同梱スクリプト | 決定的な処理すべて |

サブエージェントが使えない環境（プラグインのエージェントが未登録）では、`general-purpose` に
`agents/inventory-extractor.md` / `agents/inventory-verifier.md` の本文を読ませて同じ役割を与える。

## 準備

- スクリプトは `${CLAUDE_SKILL_DIR}/scripts/` にある。**`python <スクリプトの絶対パス> 引数…` の形で1回に1本だけ**実行する。
  シェル変数（`S=…; python $S/…`）・`cd`・`&&` や `;` での連結を使うと許可ルールに一致せず拒否される
- 依存: python3（標準ライブラリ）と PyYAML（検出ルールの読み込みのみ）。無ければ `pip install pyyaml` をユーザーに依頼する
- 作業ディレクトリ `W` は対象リポジトリの外に作る（既定: スクラッチパッド配下の `inventory-<システム名>/`）。
  中断しても `W` が残っていれば途中から再開できる
- データ形式は `references/schema.md`、検出ルールの書き方は `references/detectors.md`
- 以下、対象リポジトリを `R` とする
- **権限の準備（Phase 2 の前に必須）。** 抽出担当・検証担当は `R` を読み、`W` を読み書きする。
  `R` がセッションの作業ディレクトリ外なら `/add-dir R` で追加するよう、ユーザーに依頼する。
  `W` を既定のスクラッチパッド以外に置く場合は、`W` への書き込みも許可してもらう。
  許可が無いと、並列で動く各エージェントが確認待ちで止まるか、書き込めずに終わる
- スキーマは `slice_brief.py` / `features.py sample` が `W/schema.md` に写す。エージェントにはこちらを渡す
  （プラグインのディレクトリへの読み取り許可を不要にするため）

## Phase 0: 偵察と見積もり

1. ファイル一覧を作る
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/build_file_manifest.py --repo R --work W
   ```
   要約を読み、スタックと構成を判定する。特に次を確認する
   - 「除外したディレクトリ」に業務コード（例: 取引先を意味する `vendor/`、`build/` という名の業務モジュール）が無いか。
     あれば `--include '<glob>'` で戻す
   - 「行数の多い対象ファイル」にシード・ダンプ・翻訳データ・フィクスチャがあれば `--exclude` を検討する
   - git 未追跡のファイルが対象外になっている旨の警告があれば、ユーザーに確認する
   - モノレポで一部だけが対象なら `--subdir`
2. 構成ファイル（`package.json`、`pyproject.toml` 等）とディレクトリ構成だけを見て、使っている
   フレームワークを特定する。コード本体は読まない
3. 検出ルールを選ぶ。同梱: `fastapi` / `nextjs` / `python` / `data` / `generic`（主要フレームワーク・ファイルベースルーティング・cron）。
   同梱で拾えないエントリーポイントの書き方があれば、`references/detectors.md` に従って `W/detectors/<名前>.yaml` を書く
4. エントリーポイント一覧を作る（**選んだ検出ルールだけ**を並べる。例は FastAPI + Next.js の場合）
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/enumerate_entrypoints.py --work W --detectors ${CLAUDE_SKILL_DIR}/detectors/fastapi.yaml ${CLAUDE_SKILL_DIR}/detectors/nextjs.yaml ${CLAUDE_SKILL_DIR}/detectors/python.yaml ${CLAUDE_SKILL_DIR}/detectors/data.yaml
   ```
   - 主要な種別（API・画面・ジョブ）が 0 件なら検出ルールが合っていない。代表的なものは `grep -c` 等の別手段で件数を突き合わせる
   - 「除外したファイルの中にエントリーポイント候補がある」警告が出たら、手順 1 に戻って除外を見直す
5. 担当範囲に分割して見積もる
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/plan_slices.py --work W --max-lines 5000
   ```
6. **ユーザーに承認を取る（必須）。** 次を提示する
   - 対象規模（ファイル数・行数）、除外したもの、対象外の役割（既定: doc。test は抜粋読み）
   - エントリーポイントの件数（種別ごと）と、追加した検出ルール
   - 担当範囲の数と概算トークン。**本実行の前に、いくつかの担当範囲だけで試行して実測値で補正する**こと

## Phase 1: 試行

本実行の前に、典型的な担当範囲 2〜3 件（API 層・画面層・ドメイン層など性質の違うもの）だけを Phase 2〜3 の手順で処理する。

- サブエージェントの完了通知にある使用トークンから「1行あたりトークン」を求め、
  `plan_slices.py --dry-run --tokens-per-line <実測値>` で全体の見積もりを出し直してユーザーに伝える
- 抽出結果の質を、1つの担当範囲の分だけ確認する（ここだけは進行役が extract JSON を読んでよい）。
  機能の粒度・名前の付け方・対象外への振り分けがずれていれば、依頼文に補足を足してから本実行する
- 見積もりが大きく変わったら、続行するかユーザーに確認する

## Phase 2: 抽出（並列）

1. 指示書を書き出す
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/slice_brief.py --work W --pending
   ```
2. 出力された未抽出の担当範囲ごとに `inventory-extractor` を起動する。**同時起動は 5〜8 体まで**。
   依頼文は短く、可変部分を最後に置く（各エージェントで共通の前置きがキャッシュされる）:
   ```
   機能一覧の抽出。スキーマ: W/schema.md
   指示書: W/briefs/S5bde43.md
   ```
3. 完了通知は1行の要約だけを受け取る。抽出 JSON は読まない

## Phase 3: 自動検証と差し戻し

```
python ${CLAUDE_SKILL_DIR}/scripts/verify_evidence.py --work W
```

- 不合格の担当範囲があれば `slice_brief.py --pending` を再実行する。不合格の担当範囲の指示書は
  **修正依頼**（エラー一覧だけ）になるので、同じく `inventory-extractor` に渡す。全文の再抽出はさせない
- verify が「3 回以上不合格」と出した担当範囲は、エラー内容をユーザーに見せて判断を仰ぐ（分割・除外など）
- すべての担当範囲が合格したら、網羅率を確認する
  ```
  python ${CLAUDE_SKILL_DIR}/scripts/check_coverage.py --work W
  ```
  - 「一覧に無かったエントリーポイントの報告」が多い種別は検出ルールを直し、Phase 0 の 4・5 からやり直す
    （担当範囲 ID は内容ハッシュ由来なので、中身が変わらない担当範囲の抽出・検証結果はそのまま有効）
  - 「読まない役割のファイル内」のエントリーポイントがあれば、その役割を読む（`--skip-role` を変える）か、除外するかを決める
  - 種別ごとの対象外率が高い（例: API の 3 割以上が対象外）なら、抽出の振り分けを疑う

## Phase 4: 集約

1. 要約一覧を作る（合格済みの担当範囲だけが載る）
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/features.py digest --work W
   ```
   集約前の機能が 1,500 件を超えるなど一度に読めない量なら `--prefix <ディレクトリ>` で分けて作り、
   ドメインごとに grouping ファイルを分けて書く
2. `W/digest.txt` だけを読み、`W/grouping.json` を書く（形式は `references/schema.md`）
   - ドメインは業務のまとまり（会員管理・受注・請求…）で切る。技術レイヤー（API・画面）では切らない
   - 同じ業務操作の API 側と画面側の集約前の機能は、1つの機能にまとめる（sources に両方）
   - `actor_map` に digest 末尾の「集約前の利用者表記」をすべて書き、統一語彙に写像する
   - sources が1件の機能には summary を書かない（集約前の要約がそのまま使われる）
   - sources が2件以上の機能の summary は集約前の要約の統合にとどめる。集約前の要約に無い事実を足さない
3. マージする（配置漏れ・重複配置・actor_map 漏れがあれば不合格になるので直して再実行）
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/features.py merge --work W --grouping W/grouping.json
   ```

## Phase 5: 独立検証

1. 検証対象のバッチを作る（推定・不明、エントリーポイントなし、統合要約、制約ありの機能を優先し、残りは無作為。
   対象外にしたエントリーポイントの抜き取りも含める）
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/features.py sample --work W --n 15 --entries 10
   ```
   機能数が 200 を超える規模なら `--n` を全体の 5〜10% 程度に増やす
2. `W/review-batches/` のバッチごとに `inventory-verifier` を起動する。依頼文はバッチファイルのパスとスキーマのパス（`W/schema.md`）だけ
3. 検証担当の結果も自動検証する
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/verify_evidence.py --work W --review W/review/b01.json
   ```
4. 指摘を元の担当範囲に差し戻す
   ```
   python ${CLAUDE_SKILL_DIR}/scripts/slice_brief.py --work W --from-review W/review/b01.json [W/review/b02.json ...]
   ```
   出力された修正の指示書ごとに `inventory-extractor` を起動し、`verify_evidence.py` → `features.py merge` からやり直す。
   統合要約の誤りなら grouping.json を直して merge する
5. 誤りの傾向（例: 権限の例外を書き落とす）が見えたら、同じ観点で追加の抜き取りを行う。
   `should_be_feature` が出たら、同じ理由コードの対象外エントリーポイントを追加で検証する
6. 誤り率が高い（例: 20% 超）なら、抽出の依頼文を見直してから該当する担当範囲を再抽出する

## Phase 6: 出力

```
python ${CLAUDE_SKILL_DIR}/scripts/check_coverage.py --work W
python ${CLAUDE_SKILL_DIR}/scripts/render_inventory.py --work W [--out-dir <出力先>]
```

- `feature-inventory.xlsx`（シート: 概要 / 機能一覧 / API一覧 / 画面一覧 / エントリーポイント一覧 / 要確認。オートフィルタ・見出し固定）
- `feature-inventory.html`（1ファイル完結。検索・ドメイン/確信度/エントリーポイントの有無で絞り込み・行クリックで詳細）
- `feature-inventory.md`（差分確認・エージェント向け）
- 元データは `features.json`。出力物は手で直さない（直すなら grouping.json か抽出結果を直して再生成）

完了報告では次をユーザーに伝える。

- 出力ファイルのパス
- ファイル網羅率・エントリーポイントの対応率・確信度の内訳
- 独立検証の結果（機能・対象外のエントリーポイントそれぞれの誤り件数と、直したか）。抜き取りであり全件保証ではないこと
- 読んでいない範囲（除外・対象外の役割）と、要確認事項の件数
- 実際に使ったサブエージェント数と概算トークン

## トークンを節約する仕組み

| 手段 | 効果 |
|---|---|
| 列挙・分割・照合・集約・出力をすべてスクリプトで行う | LLM が読むのはコードと短い要約だけ |
| スクリプトの標準出力は要約だけ。全件はファイルへ | 進行役のコンテキストが規模に比例して膨らまない |
| 生成物・ロック・minify・巨大データ・重複ファイルを除外 | 機能に関係ない行を読まない |
| テストは抜粋読み（テスト名・定義行のみ） | テストの行数の大半を読まずに、挙動の手がかりは残す |
| ディレクトリ境界で詰めた担当範囲（既定 5,000 行） | 1体あたりの固定コスト（指示・スキーマの読み込み）を薄める |
| 試行で1行あたりトークンを実測（実測例: 約 35/行） | 本実行前に総額を把握し、規模に応じて上限や除外を調整できる |
| 抽出担当の応答は1行。結果はファイル渡し | 完了通知で進行役の文脈が膨らまない |
| 不合格・検証指摘はエラー一覧だけを渡して修正（実測で初回の約半分） | 担当範囲の全文再読を避ける |
| 担当範囲 ID が内容ハッシュ由来 | 検出ルールの修正後・コード更新後も、中身が同じ担当範囲は再抽出しない |
| 集約は1行ずつの要約一覧から | 集約前の機能の JSON をすべて読まなくてもグループ分けできる |
| 独立検証はリスク順の抜き取り | 全件再検証のコストを払わずに誤りの傾向をつかむ |

さらに削る必要があるときの調整（ユーザーに確認してから行う）:

- `--max-lines` を上げる（7,000 程度まで。上げすぎると読み落としが増える）
- 機能に関係の薄いディレクトリ（CI、開発スクリプト、デモ）を `--exclude` で外す
- `--outline-role test,config` で設定ファイルも抜粋読みにする

## コードが更新されたとき

同じ `W` で Phase 0 の 1・4・5 を再実行する。中身が変わった担当範囲だけが新しい ID になり、
`slice_brief.py --pending` はそれだけを出す（旧 ID の抽出結果は `extract/_stale/` に退避される）。
以降は Phase 2 から進める。grouping.json の旧 ID は merge で「存在しない集約前の機能」として不合格になるので、
digest を見て新しい ID に差し替える（取り違えは起きない）。
