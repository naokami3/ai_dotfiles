# system-inventory-ja

1つのシステムのコード全体から、**漏れと捏造を仕組みで抑えた機能一覧**を作る Claude Code プラグイン。
成果物は Excel（.xlsx）・HTML・Markdown の3形式です。

普段の開発では、変更の影響範囲だけを読めば足ります。しかし、システムの統合や移行の前には全体像を正確に
把握する必要があります。そこで全コードを1つのエージェントに読ませると、コンテキストが溢れて詳細が落ち、
名前からの推測で「ありそうな機能」を書いてしまいます。このプラグインは、その失敗を仕組みで防ぎます。

対象は1システムです。複数システムの比較・対応付けは扱いません。

## 用語

| 用語 | 意味 |
|---|---|
| エントリーポイント | 外から機能を呼び出せる箇所。API のエンドポイント、画面の URL、定期実行ジョブ、CLI コマンド、DB テーブルなど |
| ファイル一覧・エントリーポイント一覧 | 漏れなく読むべき全件の一覧。スクリプトが機械的に作り、網羅率はこの一覧に対して数える |
| 検出ルール | エントリーポイントを見つけるための正規表現（`detectors/*.yaml`）。フレームワークごとに用意する |
| 担当範囲 | 1体のサブエージェントが読むコードのまとまり（数千行）。コード全体をディレクトリ単位で区切って作る |
| 指示書 | 担当範囲ごとにスクリプトが作る、サブエージェント向けの指示（読むファイル・対応付けるエントリーポイントなど） |
| 根拠 | 書いた内容の裏付けとなる `ファイル:行` と、その行の文字列の引用 |
| 読了確認 | 本当に読んだかを確かめるため、スクリプトが無作為に選んだ行の内容を答えさせる仕組み |
| 抜粋読み | テストなど、テスト名・定義の行だけを読む読み方（全文は読まない） |
| 集約前の機能 | 担当範囲ごとに抽出した機能。画面側と API 側のように、同じ操作が別々に出てくることがある |
| 集約 | 集約前の機能を業務のまとまり（ドメイン）ごとに整理し、同じ操作をまとめること |
| 要確認事項 | コードだけでは断定できなかった点。「何が未確認か」と「どう確かめるか（読むファイル・試す操作・聞く相手）」を対で書く |
| 独立検証 | 抽出したエージェントとは別のエージェントが、抜き取った機能をコードと照合し直すこと |
| 進行役 | このスキルを起動したセッション。全体を進めるだけで、自分ではコードを読まない |
| 試行 | 本実行の前に、いくつかの担当範囲だけで実行してトークン量を実測すること |

## 構成

| 種別 | 名前 | 役割 |
|---|---|---|
| スキル | `build-feature-inventory` | 進行役。手順の実行・判断・ドメインへのグループ分け |
| エージェント | `inventory-extractor`（Sonnet） | 1つの担当範囲を読み、根拠付きで機能を抽出する |
| エージェント | `inventory-verifier`（Sonnet） | 集約済みの機能をコードと照合する（独立検証） |
| スクリプト | `scripts/*.py` | 一覧作成・担当範囲への分割・引用の照合・網羅率・集約・出力 |
| 検出ルール | `detectors/*.yaml` | エントリーポイント（API・画面・ジョブ・CLI・テーブル）を列挙する正規表現 |

## 仕組み

```
Phase 0 偵察と見積もり : ファイル一覧とエントリーポイント一覧をスクリプトで作り、担当範囲の数と概算トークンを提示 → 承認
Phase 1 試行           : 2〜3 個の担当範囲で実行し、トークン量を実測して見積もりを補正
Phase 2 抽出（並列）   : 担当範囲ごとにサブエージェントが読み、根拠付きで機能を JSON に書く
Phase 3 自動検証       : 引用がその行に実在するか・全エントリーポイントが対応付いたか・指定範囲を読んだかを照合。
                         不合格ならエラーだけを伝えて修正を依頼する
Phase 4 集約           : 1行ずつの要約一覧を見てドメインに分ける。エントリーポイント・データ・根拠はスクリプトが引き継ぐ
Phase 5 独立検証       : リスクの高い機能から別のエージェントが抜き取って照合
Phase 6 出力           : features.json（すべての出力の元データ）から xlsx / html / md を生成
```

### ハルシネーションと漏れの抑え方

| 仕組み | スクリプトで保証できる範囲 |
|---|---|
| ファイル一覧（`git ls-files` 由来）とエントリーポイント一覧を「漏れなく読むべき全件」とし、網羅率を数値で出す | 一覧内の網羅。除外したファイル内にエントリーポイントらしきものがあれば警告する |
| 担当範囲ごとに新しいサブエージェントが読む。進行役はコードを読まない | — |
| 読了確認（スクリプトが選んだ行の内容を答えさせる） | 指定した行を実際に読んだこと |
| すべての主張に根拠（`ファイル:行` と引用）を付けさせ、その行に実在するか照合する | 引用した文字列が実在すること |
| 利用者・制約（〜のみ・〜できない）は1件ずつ根拠の行を必須にする | 根拠の行が示されていること |
| 集約で書けるのは名前・グループ分け・利用者表記の統一だけ。まとめなかった機能は集約前の要約をそのまま使う | エントリーポイント・データ・根拠・制約・確信度は書き換えられない |
| 別のエージェントが、機能と「対象外にしたエントリーポイント」をリスク順に抜き取ってコードと照合する | 抜き取った範囲のみ（統計的） |

**意味の正しさはスクリプトでは保証できません。** そのため、独立検証の結果（誤り率）と確信度・要確認事項を
成果物に必ず残します。

担当範囲と機能の ID は内容から決まります。再実行や再集約をしても、検証結果や参照が別の機能に
付け替わることはありません。

### トークンの節約

- 決定的な処理はすべてスクリプトが行い、画面に出すのは要約だけにする
- 生成物・ロックファイル・minify 済み・巨大データ・重複ファイルを除外する
- テストは抜粋読みにする
- 試行で1行あたりのトークンを実測してから本実行する
- 不合格のときはエラー一覧だけを渡して直させる
- 内容が変わっていない担当範囲は抽出結果を引き継ぐ（コード更新後や検出ルール修正後も差分だけ再実行）
- 独立検証はリスク順の抜き取りにする

## 成果物

| ファイル | 内容 |
|---|---|
| `feature-inventory.xlsx` | シート: 概要 / 機能一覧 / API一覧 / 画面一覧 / エントリーポイント一覧 / 要確認（オートフィルタ・見出し固定） |
| `feature-inventory.html` | 1ファイル完結。機能・API・画面・エントリーポイント・要確認のタブ。検索、ドメイン・確信度での絞り込み、行クリックで詳細表示 |
| `feature-inventory.md` | 差分確認・エージェント向け |
| `features.json` | 元データ。上の3つはここから生成する |

## 対応スタック

ファイル一覧・担当範囲への分割・検証は言語に依存しません。エントリーポイントの列挙は検出ルールによります。

- 同梱: FastAPI、Next.js（App / Pages Router）、Python のジョブ・CLI・ORM、SQL・Prisma・Drizzle 等のデータ定義、
  Express 系・NestJS・Spring・ASP.NET・Go・Rails・Laravel のルート、ファイルベースルーティング
  （TanStack Router / Remix / SvelteKit / Nuxt）、cron 類
- 同梱で拾えないスタックでは、Phase 0 で検出ルールの YAML を追加します（`references/detectors.md`）

## 必要なもの

- Python 3.9 以上
- PyYAML（`pip install pyyaml`。検出ルールの読み込みにのみ使用）
